# Contributing

OpsWiki for Codex uses GitHub Flow.

## Branch Strategy

- All work must happen in a feature branch.
- Do not commit directly to `main`.
- Open a Pull Request before merging into `main`.
- Keep each Pull Request small and reviewable.

## Allowed Branch Name Prefixes

- `feature/`
- `fix/`
- `docs/`
- `refactor/`
- `test/`
- `chore/`
- `release/`

## Forbidden Branch Name Prefixes

- `codex/`
- `ai/`
- `auto/`
- `generated/`
- `bot/`

## Recommended Initial Branch

```text
feature/init-opswiki-codex-plugin
```

## Commit Message Convention

Use Conventional Commits.

Allowed commit types:

- `feat`
- `fix`
- `docs`
- `refactor`
- `test`
- `chore`
- `ci`
- `build`
- `perf`
- `style`
- `revert`

## Commit Message Rules

- Use lowercase commit type.
- Use imperative mood.
- Keep the subject line concise.
- Do not include `Codex`, `AI-generated`, `Generated by Codex`, or similar phrases in commit messages.
- Do not include co-author metadata unless explicitly requested.
- Do not include secrets, credentials, tokens, or personal access keys.

Good examples:

```text
feat: initialize opswiki codex plugin structure
docs: add devops runbook templates
docs: add terraform review checklist
refactor: reorganize skill references
chore: add local plugin marketplace example
```

Bad examples:

```text
codex: create plugin
ai: generate files
feat: generated by Codex
chore: update stuff
initial commit
```

## Design Principles

- Be practical for real DevOps/MLOps workflows.
- Prefer small, reviewable files.
- Avoid over-engineering.
- Avoid claiming production readiness.
- Do not include secrets or credentials.
- Use clear Markdown documentation.
- Keep examples generic and safe.
- Clearly separate confirmed facts, assumptions, verification steps, and resolution steps in runbook-related content.
